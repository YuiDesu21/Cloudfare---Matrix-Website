# Website audit (October 6, 2026)

This audit covers the staging project `sssfvmyukpmzbktdlybg` and local build. No live migration or deployment was performed.
The existing Junel staging account was granted Admin and Owner access with user approval for the UI audit; the live account and project were not changed.

## Findings that still affect a live rollout

1. Patronizing Income now offers all four requested entry choices in staging. The rollback-only payment and activation tests pass, but staging has no active Timeline packages, so the populated PHP 2,800 package browser and a real signed-in package checkout have not yet been rehearsed visually.
2. The staging dataset has no placed members or nonzero balances. A temporary, unpaid top-up request confirmed the populated Funds approval card and pending-count behavior, then was removed with zero credits. Matrix progress, discount redemption, actual partial income transfers, contract rollovers in the browser, and withdrawal completion have not been exercised end to end. SQL smoke tests are rollback-only and are not a substitute for a signed-in pilot with representative data.
3. The October 6 live database archive was restored successfully into an offline local Supabase PostgreSQL 17 database on D:. The snapshot contained zero Storage buckets and objects. Recheck current live Storage and take a fresh database backup immediately before live migrations; this rehearsal does not prove a later backup will restore.
4. The token and investment offerings need independent Philippine legal review before public enrollment or promotion. No legal authority is inferred from corporate registration alone.
5. Supabase Auth's leaked-password protection remains disabled in staging. Enable and test it in the project settings before launch.
6. F3 wallet entry currently accepts any nonempty value up to 52 characters. The correct chain/address format needs a business rule before technical validation can be added; manual token delivery should verify the destination in the meantime.
7. Staging's security advisor still reports many signed-in callable SECURITY DEFINER functions. Many are intentional app endpoints, but their authorization checks need a function-by-function review before this is treated as a security sign-off.
8. Owner Finances is an older, partial report. Its net cash figure mixed direct 1200 payments with all withdrawals and was removed from the UI. A complete owner cash and liability report must be designed across commerce, top-ups, Budget, Patronizing, investments, and Main Funds before this screen can support financial decisions.

## Fixes verified in this checkout

- The local static server no longer serves source files or `.env` paths.
- Production member navigation now targets the built entry-activation filename.
- Cached member data is discarded when the Supabase session changes or signs out.
- Order history retains older records and separates terminal from active orders; the lists scroll.
- Main Funds submit controls recover after request errors; withdrawal pages display load errors.
- Password reset uses the same minimum length and letter/number rule as sign-up.
- Passive Income History includes Budget Plan, Patronizing source filtering, and partial-transfer balances. A focused regression test checks the available balance math.
- Staging migration `202610060002` removes anonymous execution of two internal helper functions; admin access still loads after the change.
- Staging migration `202610060003` applies the Owner-only self-review exception to Budget investment approvals. Rollback-only tests confirm a regular admin cannot approve their own investment, while the Owner can.
- Owner Finances now states its limited scope and no longer displays a misleading overall net cash amount.
- Admin navigation now left-aligns when tabs overflow, keeping Overview and Pending Requests reachable at a narrow viewport.
- Staging migrations `202610060004` through `202610060006` add the 12 F3 / PHP 720 and Timeline-package / PHP 2,800 Patronizing entries, keep old tiers intact, isolate package purchases from Timeline Matrix activation, serialize competing entry paths, and restrict internal trigger helpers.
- Patronizing entry cards now use a two-column tablet layout and a single-column phone layout. Checkout pages identify the chosen Patronizing purpose and link back to the plan.

It contained 781 archive objects, 28 public tables, 6 Auth users, 6 profiles, 4 matrix positions, 18 reward rows, 52 migrations through `202609090002`, and no Storage buckets or objects.
